# pdn_mask — Модуль безопасности персональных данных

Прокси-сервис между системой-потребителем и LLM: находит персональные данные в тексте,
маскирует их перед отправкой в модель и демаскирует ответ обратно. Хакатон «Модуль
безопасности персональных данных» — требования и контракт API см. `ds.pdf` (ТЗ трека).

---

## Для проверяющих: как всё устроено и как проверить

**Сервис развёрнут и доступен по адресу:** `http://31.184.218.30/process`
(HTTP, без TLS — по ТЗ для проверки этого достаточно, `ssl_verify=false`).

### Контракт `POST /process`

Один эндпоинт на два направления. Направление определяется состоянием `payload_id`
на стороне сервиса, а не отдельным полем в запросе — это требование контракта (Приложение A
ТЗ), а не наше решение.

```
POST /process
Content-Type: application/json

{ "payload": "<строка>", "payload_id": "<идентификатор>" }
  → 200 OK
{ "result": "<строка>" }
```

| Шаг | Запрос | Что делает сервис | Ответ |
|---|---|---|---|
| 1. Маскирование | новый `payload_id`, `payload` = исходный текст | находит ПДн, маскирует, сохраняет пару (оригинал / маска) в БД по `payload_id` | замаскированный текст |
| 2. Демаскирование | уже встречавшийся `payload_id` (любой `payload`) | достаёт сохранённый оригинал по `payload_id` | исходный текст |

Повторный запрос с тем же `payload_id` на любом из двух шагов — идемпотентен: отдаётся
тот же результат, что и в первый раз, без пересчёта. На шаге демаскирования сервис
сверяется только с `payload_id`, а не с содержимым присланной маски — это специально
сделано так, чтобы демаскирование не ломалось, если LLM переформулировала текст вокруг
токенов.

### Проверить работоспособность

```bash
# health-check — модель загружена и БД доступна
curl -s http://31.184.218.30/health

# шаг 1: маскирование
curl -s -X POST http://31.184.218.30/process \
  -H "Content-Type: application/json" \
  -d '{"payload":"Меня зовут Иван Петров, паспорт 4509 123456, телефон +7 912 345-67-89","payload_id":"check-1"}'
# → {"result":"Меня зовут [ФИО_1], паспорт [Паспорт_1], телефон [Телефон_1]"}

# шаг 2: демаскирование — тот же payload_id, любой payload
curl -s -X POST http://31.184.218.30/process \
  -H "Content-Type: application/json" \
  -d '{"payload":"неважно что здесь","payload_id":"check-1"}'
# → {"result":"Меня зовут Иван Петров, паспорт 4509 123456, телефон +7 912 345-67-89"}
```

`/health` отвечает `200` при исправной модели и БД, иначе `503` с телом
`{"status":"error","model_loaded":bool,"database":"ok"|"unavailable"}`.

### Что маскируется

Все 22 типа персональных данных из ТЗ: ФИО, дата/место рождения, серия и номер паспорта,
гражданство, орган и дата выдачи паспорта, код подразделения, серия и номер в/у, адрес
(страна/индекс/город/улица/дом/квартира отдельно), email, телефон, ИНН, номер карты, CVV,
PIN-код, держатель карты. Полный список с регулярками — `pii_service/config.py` (`PII_TYPES`).

Не считаются персональными данными и не маскируются: упоминания публичных персон
(например, поэт Александр Пушкин) и адреса отделений банка — это отдельно проверяется
эвристикой в `pii_service/context.py`.

### Статус: инфраструктура поднята, MVP работает end-to-end

Задеплоено на сервере (31.184.218.30) через Docker Compose, CI/CD автоматический
(пуш в `main` → GitHub Actions деплоит). Контракт `/process` реализован и проходит
базовую проверку. Качество детекта (95% по ТЗ), настройка по потребителям, 429/деградация,
метрики — ещё не сделаны, это следующий этап.

### Архитектура

```
Consumer → POST /process → [Regex-слой] → [NER-слой] → [merge/context-арбитраж] → [masking]
                                                                                       ↓
                                                              Postgres (пара оригинал/маска по payload_id,
                                                                     init_text зашифрован Fernet)
```

Хранилище — Postgres (`pii_service/storage.py`), не Redis: по каждому `payload_id`
сохраняется пара (исходный текст, замаскированный текст); исходный текст в БД хранится
зашифрованным (`cryptography.Fernet`, ключ — `PII_ENCRYPTION_KEY` в `config.py`), время
хранения — `RETENTION_DAYS` (по умолчанию 30 дней). На шаге демаскирования сервис просто
отдаёт сохранённый оригинал по `payload_id`, не сверяя присланный `payload` с маской —
см. таблицу шагов выше.

## Структура репозитория

```
pii_service/
  config.py    — реестр типов ПДн (PII_TYPES), пороги score, списки-словари
                 (публичные персоны, маркеры адреса/организации/личной принадлежности,
                 страны для гражданства), настройки БД и пула воркеров. ГЛАВНОЕ МЕСТО
                 для расширения списка типов — см. "Как добавить новый тип ПДн" ниже.
  patterns.py  — regex-детект: карта (+ Луна), ИНН (+ контрольная цифра), паспорт
                 (в т.ч. "серия XXXX номер XXXXXX"), в/у, email, телефон, даты (числом
                 и текстом, разные форматы), индекс/адрес, держатель карты и т.д.
                 find_regex(text) — точка входа.
  ner.py       — NER-модель (Babelscape/wikineural-multilingual-ner) для ФИО/адресов/
                 организаций, разбиение длинного текста на чанки. find_ner,
                 find_organizations, build_addresses — точки входа.
  context.py   — арбитраж и разрешение конфликтов между слоями: merge() убирает
                 пересечения находок, apply_context() решает вопрос "это персональные
                 данные или нет" (Пушкин-поэт vs Пушкин-клиент, адрес отделения банка
                 vs адрес проживания и т.п.) — здесь же живёт эвристика по PUBLIC_PERSONS/
                 PUBLICITY_MARKERS/ADDRESS_NAME_MARKERS/ORG_MARKERS из config.py.
  masking.py   — mask(text, findings) → (masked_text, mapping). Токены вида [ФИО_1],
                 [ИНН_1]; одинаковое (после нормализации) значение одного типа получает
                 один и тот же токен. unmask() в текущем пайплайне не вызывается — см.
                 storage.py ниже.
  storage.py   — хранилище в Postgres: по каждому payload_id сохраняется пара
                 (исходный текст — зашифрован Fernet, замаскированный текст — открыт).
                 load_request(payload_id) отдаёт расшифрованный оригинал. Демаскирование
                 работает через это хранилище, а не через mapping/unmask() — устойчивее
                 к переформулировке текста LLM.
  api.py       — FastAPI, точка входа сервиса: эндпоинт /process (контракт) и /health.
                 Пайплайн (regex+NER, CPU-bound) гоняется в ThreadPoolExecutor
                 (PIPELINE_EXECUTOR_WORKERS в config.py), чтобы не блокировать event loop.
  run.py       — запуск сервера (python run.py). Не обычный uvicorn.run() — см. docstring
                 в файле про SelectorEventLoop и psycopg async.
  app.py       — ПРЕЖНЯЯ версия на Redis, из пайплайна деплоя больше не используется
                 (оставлена для истории, будет удалена).
  tests/       — pytest (test_api.py, test_masking.py, test_storage.py).

check.py       — ручной прогон пайплайна на нескольких примерах (python check.py).
sql/init.sql   — схема Postgres (pii_masker.pii_requests), накатывается storage.py сам
                 при старте сервиса.
Dockerfile, docker-compose.yml — app (FastAPI+Uvicorn, python pii_service/run.py) + postgres,
                                  порт 80 → 8000.
.github/workflows/deploy.yml   — на пуш в main: ставит Docker на сервере (если нет),
                                  git pull, docker compose up -d --build.
```

## Как добавить новый тип ПДн (для регулярных/структурных типов)

1. Добавить словарь в `PII_TYPES` в `config.py` (type, label, pattern/validator, keywords,
   base_score).
2. Если нужна валидация (контрольная сумма, диапазон дат и т.п.) — функция в `patterns.py`,
   по образцу `luhn_check`/`inn_check`/`date_check`.
3. Если тип требует NER (не регулярка, а "любое ФИО/место") — расширять `ner.py`.
4. `masking.py`, `storage.py` и `api.py` менять не нужно — они уже работают с произвольным
   списком типов через `config.get_pii_type()`.

Это и есть то самое требование ТЗ "добавлять новые правила без переделки всего сервиса" —
оно уже выполняется на уровне конфига.

## Производительность — почему сейчас не выдержит 1000 RPS / ≤1с

Контракт (Приложение B) требует latency ≤1с и RPS 1000 (доп. плюс — 2000), тексты до
100k токенов, "элементы датасета переиспользуются". Часть пунктов из первой версии этого
раздела уже закрыта переходом на `api.py`/`storage.py` (async БД, пайплайн в threadpool,
подобранный размер пула — см. комментарий `PIPELINE_EXECUTOR_WORKERS` в `config.py` с
результатами собственного нагрузочного теста). Что осталось — по приоритету:

1. **NER — главное узкое место.** `ner.find_ner` гоняет полноразмерный мультиязычный
   BERT (`Babelscape/wikineural-multilingual-ner`) на CPU. Это единицы-десятки
   инференсов в секунду на процесс — без решения этого пункта остальное не имеет смысла.
   - Заменить на лёгкую CPU-модель для русского (natasha/slovnet — CRF, не transformer)
     либо квантовать текущую в ONNX int8 (`optimum`+`onnxruntime`, обычно 2-4x на CPU).
   - Или микробатчинг: собирать запросы в окне ~10-20мс в один батч на инференс
     (torch/transformers поддерживают нативно) — сложнее в реализации, но даёт прирост
     throughput без смены модели.
   - В `config.py` уже есть задел под GPU (`NER_DEVICE = "dml"`), но `run_gpu.py` и
     `requirements-gpu.txt`, на которые ссылается комментарий, ещё не созданы.

2. **Кэш по хэшу текста, не по payload_id.** ТЗ прямо говорит, что элементы датасета
   переиспользуются — один и тот же текст прилетит многократно (с разными payload_id).
   Сейчас `storage.load_request` матчит только по `payload_id`, а detect-пайплайн
   заново считается для каждого нового `payload_id`, даже если текст такой же. Кэш
   detect-результата по `sha256(payload)` — дёшево реализовать, велика отдача именно
   под профиль этой проверки.

3. **FPE для карты/ИНН/паспорта** (`ff3`/`pyffx`, детерминированное шифрование с
   сохранением формата) — эти типы не требуют ни NER, ни похода в БД: маскирование
   и демаскирование — чистый расчёт. Плюс закрывает доп. плюс по ТЗ (п.6).

4. **Backpressure вместо роста latency.** Нет ограничения на конкурентность сверх
   размера `PIPELINE_EXECUTOR_WORKERS` — при переполнении запросы просто встанут в
   очередь executor'а, а не получат быстрый ответ. Нужно: при полном пуле — сразу `429`
   с `Retry-After` (ТЗ прямо считает это ожидаемым поведением под нагрузкой), а не
   ожидание в очереди сверх 1с.

5. **Число процессов не синхронизировано с CPU сервера.** `run.py` поднимает один
   процесс uvicorn без `--workers` (конкурентность — только через
   `PIPELINE_EXECUTOR_WORKERS` внутри процесса и GIL). Проверить: даёт ли несколько
   процессов (за общим Postgres) прирост поверх текущего порога threadpool'а —
   собственный тест коллег уже показал, что больше потоков внутри процесса не помогает
   (узкое место — GIL при работе с torch), но отдельные процессы обходят это ограничение.

6. **Чанки большого текста обрабатываются последовательно.** `ner.split_into_chunks`
   режет текст на куски под лимит модели, но `find_ner` идёт по ним в цикле. Для
   текстов ближе к 100k токенов чанки нужно гнать параллельно (ThreadPoolExecutor —
   torch-операции отпускают GIL на время вычислений, потоки реально параллелятся).

## Локальный запуск

```bash
docker compose up --build
curl -X POST http://localhost/process -H "Content-Type: application/json" \
  -d '{"payload":"Иван Петров, паспорт 4509 123456","payload_id":"test-1"}'
```

Без Docker — `pip install -r requirements.txt`, нужен локальный Postgres (см.
`DATABASE_URL` в `config.py`), запуск — `python pii_service/run.py`. Без БД и HTTP —
`python check.py` (прогон пайплайна на нескольких примерах в коде). Тесты —
`pytest pii_service/tests/`.

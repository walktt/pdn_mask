# pdn_mask — Модуль безопасности персональных данных

Прокси-сервис между системой-потребителем и LLM: находит персональные данные в тексте,
маскирует их перед отправкой в модель и демаскирует ответ обратно. Делается для хакатона
«Модуль безопасности персональных данных» (Банк, требования — см. ТЗ трека и контракт API,
оба файла приложены в проекте в claude.ai).

Этот файл — единая точка входа для всех, кто дорабатывает проект (включая AI-ассистентов):
что уже сделано, как это устроено, что осталось, и куда именно добавлять код.

## Статус: инфраструктура поднята, MVP работает end-to-end

Задеплоено на сервере (31.184.218.30) через Docker Compose, CI/CD автоматический
(пуш в `main` → GitHub Actions деплоит). Контракт `/process` реализован и проходит
базовую проверку. Качество детекта (95% по ТЗ), настройка по потребителям, 429/деградация,
метрики — ещё не сделаны, это следующий этап.

## Архитектура

```
Consumer → POST /process → [Regex-слой] → [NER-слой] → [merge/context-арбитраж] → [masking]
                                                                                       ↓
                                                                          Redis (vault: payload_id → mapping)
```

Один HTTP-эндпоинт `POST /process`, направление (маскирование/демаскирование) определяется
состоянием `payload_id` в Redis — это единый контракт, обязательный для проверяющей системы
(см. `ds.pdf`, Приложение A). Схема:

```
{ "payload": "<строка>", "payload_id": "<идентификатор>" }
  → 200
{ "result": "<строка>" }
```

- Новый `payload_id` → это шаг 1 (маскирование). Результат и mapping сохраняются в Redis
  (TTL 1 час, ключ `pdn:<payload_id>`).
- Тот же `payload_id`, `payload` совпадает с ранее возвращённой маской → повтор шага 1,
  отдаём тот же результат (идемпотентность/ретраи).
- Тот же `payload_id`, `payload` — не совпадает с маской → это шаг 2 (демаскирование) по
  сохранённому mapping.
- Дальнейшие повторы → отдаём сохранённый результат шага 2.

## Структура репозитория

```
pii_service/
  config.py    — реестр типов ПДн (PII_TYPES), пороги score, списки-словари
                 (публичные персоны, маркеры адреса/организации/личной принадлежности,
                 страны для гражданства). ГЛАВНОЕ МЕСТО для расширения списка типов —
                 см. "Как добавить новый тип ПДн" ниже.
  patterns.py  — regex-детект: карта (+ Луна), ИНН (+ контрольная цифра), паспорт,
                 в/у, email, телефон, даты (числом и текстом, разные форматы),
                 индекс/адрес, держатель карты и т.д. find_regex(text) — точка входа.
  ner.py       — NER-модель (Babelscape/wikineural-multilingual-ner) для ФИО/адресов/
                 организаций, разбиение длинного текста на чанки. find_ner,
                 find_organizations, build_addresses — точки входа.
  context.py   — арбитраж и разрешение конфликтов между слоями: merge() убирает
                 пересечения находок, apply_context() решает вопрос "это персональные
                 данные или нет" (Пушкин-поэт vs Пушкин-клиент, адрес отделения банка
                 vs адрес проживания и т.п.) — здесь же живёт эвристика по PUBLIC_PERSONS/
                 PUBLICITY_MARKERS/ADDRESS_NAME_MARKERS/ORG_MARKERS из config.py.
  masking.py   — mask(text, findings) → (masked_text, mapping); unmask(masked_text,
                 mapping) → original_text. Токены вида [ФИО_1], [ИНН_1]; одинаковое
                 (после нормализации) значение одного типа получает один и тот же токен.
  app.py       — FastAPI, эндпоинт /process (контракт) и /health. Состояние — в Redis.

check.py       — ручной прогон пайплайна на нескольких примерах (python check.py).
Dockerfile, docker-compose.yml — app (FastAPI+Uvicorn) + redis, порт 80 → 8000.
.github/workflows/deploy.yml   — на пуш в main: ставит Docker на сервере (если нет),
                                  git pull, docker compose up -d --build.
```

## Как добавить новый тип ПДн (для регулярных/структурных типов)

1. Добавить словарь в `PII_TYPES` в `config.py` (type, label, pattern/validator, keywords,
   base_score).
2. Если нужна валидация (контрольная сумма, диапазон дат и т.п.) — функция в `patterns.py`,
   по образцу `luhn_check`/`inn_check`/`date_check`.
3. Если тип требует NER (не регулярка, а "любое ФИО/место") — расширять `ner.py`.
4. `masking.py` и `app.py` менять не нужно — они уже работают с произвольным списком типов
   через `config.get_pii_type()`.

Это и есть то самое требование ТЗ "добавлять новые правила без переделки всего сервиса" —
оно уже выполняется на уровне конфига.

## Производительность — почему сейчас не выдержит 1000 RPS / ≤1с

Контракт (Приложение B) требует latency ≤1с и RPS 1000 (доп. плюс — 2000), тексты до
100k токенов, "элементы датасета переиспользуются". Текущая реализация под это не
рассчитана. Причины и что делать — по приоритету:

1. **NER — главное узкое место.** `ner.find_ner` гоняет полноразмерный мультиязычный
   BERT (`Babelscape/wikineural-multilingual-ner`) синхронно, по одному тексту за раз,
   на CPU. Это единицы-десятки инференсов в секунду на процесс — на 1000 RPS не хватит
   на порядки. Без решения этого пункта всё остальное не имеет смысла.
   - Заменить на лёгкую CPU-модель для русского (natasha/slovnet — CRF, не transformer)
     либо квантовать текущую в ONNX int8 (`optimum`+`onnxruntime`, обычно 2-4x на CPU).
   - Или микробатчинг: собирать запросы в окне ~10-20мс в один батч на инференс
     (torch/transformers поддерживают нативно) — сложнее в реализации, но даёт прирост
     throughput без смены модели.

2. **Кэш по хэшу текста, не по payload_id.** ТЗ прямо говорит, что элементы датасета
   переиспользуются — один и тот же текст прилетит многократно. Считать
   `sha256(payload)` и кэшировать результат detect-пайплайна (до маскирования) в
   Redis/LRU: повторный текст вообще не идёт в NER. Дёшево реализовать, велика отдача
   именно под профиль этой проверки.

3. **FPE для карты/ИНН/паспорта** (`ff3`/`pyffx`, детерминированное шифрование с
   сохранением формата) — эти типы не требуют ни NER, ни похода в Redis: маскирование
   и демаскирование — чистый расчёт. Снимает часть находок с горячего пути NER и Redis
   одновременно, плюс закрывает доп. плюс по ТЗ (п.6, токенизация/FPE).

4. **Redis — синхронный клиент в синхронном эндпоинте.** Сейчас `redis.from_url` без
   пула соединений, `def process` не `async`. Под конкурентной нагрузкой это отдельная
   точка сериализации запросов. Нужно: `redis.asyncio` с connection pool, `app.py` —
   `async def`.

5. **Backpressure вместо роста latency.** Нет ограничения на конкурентность NER —
   под нагрузкой запросы будут копиться в очереди, а не получать быстрый ответ. Нужен
   семафор на число одновременных NER-вызовов; при заполнении — сразу `429` с
   `Retry-After` (ТЗ прямо считает это ожидаемым поведением под нагрузкой), а не
   деградация latency за пределы 1с.

6. **Число uvicorn-воркеров не синхронизировано с CPU сервера.** В `Dockerfile` жёстко
   `--workers 2`. Плюс torch по умолчанию сам расхватывает все ядра потоками — при
   нескольких воркерах это oversubscription (воркеры конкурируют за одни и те же
   ядра). Нужно: `--workers` = число ядер сервера, `torch.set_num_threads(1)` /
   `OMP_NUM_THREADS=1` на воркер.

7. **Чанки большого текста обрабатываются последовательно.** `ner.split_into_chunks`
   режет текст на куски под лимит модели, но `find_ner` идёт по ним в цикле. Для
   текстов ближе к 100k токенов чанки нужно гнать параллельно (ThreadPoolExecutor —
   torch-операции отпускают GIL на время вычислений, потоки реально параллелятся).

## Локальный запуск

```bash
docker compose up --build
curl -X POST http://localhost/process -H "Content-Type: application/json" \
  -d '{"payload":"Иван Петров, паспорт 4509 123456","payload_id":"test-1"}'
```

Без Docker — `pip install -r requirements.txt`, `python check.py` (прогон пайплайна без
HTTP-обвязки на нескольких примерах в коде).
